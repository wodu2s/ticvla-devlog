모델을 고치려면 데이터가 필요하다. 앞 글에서 확인한 두 가지 — 목표의 반대쪽으로 가는 것, 가까워져도 예측 변위가 줄지 않는 것 — 를 고칠 조종 시연 데이터를 모으기로 했다.

수집을 준비하면서 세 군데서 막혔는데, **셋 다 에러를 내지 않았다.** 스크립트는 정상 종료하고 파일도 생기는데 내용이 쓸모없는 종류였다. 며칠 뒤에 발견했으면 모은 걸 통째로 버려야 했다.

## 먼저, 우리가 만들 것은 두 개뿐이다

학습 파이프라인을 뜯어보니 좋은 소식이 있었다. 윈도우 분할·좌표 변환·지시문 부착·사고 과정 텍스트 생성이 전부 원본 저장소에 이미 구현돼 있었다.

```
우리가 만드는 것
  이미지 프레임  +  trajectory.csv (시각 · 위치 · 자세)
        │
        ▼  파이프라인이 담당
  20초 윈도우 분할 → 로봇 중심 상대 좌표 변환
  → 지시문 부착 → 사고 과정 텍스트 생성
        ▼
  학습 샘플
```

라벨(미래 궤적)도 우리가 계산하지 않는다. **원본 자세 시계열만 뱉으면 파이프라인이 만든다.** 새로 짜려던 변환 스크립트가 통째로 필요 없어졌다.

CSV의 필수 컬럼도 코드에서 직접 확인했다.

```python
req = {"time", "x", "y", "z", "qx", "qy", "qz", "qw"}
if not req.issubset(df.columns): raise ValueError(...)
```

`issubset`이라 **여분 컬럼은 허용**된다. 덕분에 이미지 파일명 컬럼을 남겨서 프레임 대응을 추적할 수 있었다.

## 함정 ① 궤적이 실측이 아니라 추정이었다

이전 프로젝트에서 쓰던 수집 스크립트를 재사용하기로 했다. 이미 에피소드 단위로 프레임과 CSV를 저장하고 있었으니 형식만 맞추면 될 줄 알았다.

그런데 `trajectory.csv`를 열어보니 이렇게 적혀 있었다.

```
Estimated trajectory integrated from velocity commands.
Not ground-truth odometry.
```

**속도 명령을 적분한 추정값**이었다. 실제로 어디에 있었는지가 아니라, "이만큼 가라고 시켰으니 이만큼 갔을 것이다"였다.

이게 왜 치명적이냐면, 이 프로젝트에서 **명령과 실제가 갈라지는 사례를 이미 봤기 때문**이다. 구동계 데드존 때문에 0.09를 시켜도 바퀴가 안 도는 구간이 있었고, 안전 관문이 0.5초마다 명령을 끊던 것도 확인했다. 그 구간들이 라벨에는 "정상적으로 이동함"으로 기록된다.

**라벨이 거짓말을 하는 데이터**로 학습하면 모델은 그 거짓말을 배운다. 실측 오도메트리로 바꿨다. 기존 추정값은 버리지 않고 별도 파일로 남겨서 나중에 명령과 실제가 얼마나 벌어졌는지 비교할 수 있게 했다.

## 함정 ② 영상이 뒤집혀 있었다

카메라 노드를 띄우고 로그를 보다가 한 줄이 걸렸다.

```
nvvidconv flip-method=0
```

이 로봇은 카메라가 물리적으로 거꾸로 달려 있어서, 추론할 때는 180도 회전을 걸어 정방향으로 만든다. 그런데 수집용으로 띄운 노드는 회전이 **0**이었다.

설정 파일에는 2라고 적혀 있었는데, 노드를 직접 실행하면 그 파일을 읽지 않고 코드 기본값이 들어가는 구조였다. 런처로 띄워야 설정이 적용된다.

이대로 모았으면 **학습 영상은 뒤집혀 있고 추론 영상은 정방향**인 데이터셋이 된다. 모델은 위아래가 반대인 세상에서 주행을 배우고, 실차에서는 전혀 다른 그림을 본다. 에러 하나 없이, 그냥 아무것도 안 되는 결과가 나왔을 것이다.

여담으로, 중간에 "혹시 좌우도 뒤집혀 있나" 하고 한참 의심했다. 답은 간단했다 — **180도 회전은 상하와 좌우를 동시에 뒤집는다.** 저장된 프레임에서 바닥이 아래에 있으면 상하가 맞는다는 뜻이고, 그러면 좌우도 맞는다. 사진 한 장으로 끝날 일이었다.

## 함정 ③ 오도메트리가 한 건도 오지 않았다

가장 오래 걸렸다.

```
Publisher count: 1        노드는 살아 있고 토픽도 광고 중
hz 출력 없음              실제 메시지는 0건
```

노드는 정상 시작 메시지를 찍고 조용했다. 토픽 목록에도 나오고 발행자 수도 1인데 메시지가 안 온다.

원인은 중간 단계가 빠진 것이었다.

```
엔코더 → 관절 상태 발행 노드 → 오도메트리 노드 → 휠 오도메트리
              ↑ 이게 안 떠 있었다
```

오도메트리 노드는 **관절 상태를 받을 때만** 발행하는 구조다. 단독으로 띄우면 아무 일도 안 일어나면서 아무 경고도 안 낸다.

돌이켜보면 이전 측정들에서 계속 "오도메트리 수신 없음" 경고가 떴었다. 노드는 띄웠으니 됐겠거니 하고 넘겼는데, 그 상태로 모은 측정이 여러 건이었다.

## 그래서 코드에 거부 장치를 넣었다

세 함정의 공통점은 **실패가 성공처럼 보인다**는 것이다. 그래서 수집 스크립트에 이런 것들을 넣었다.

- **오도메트리가 안 들어오면 기록을 시작하지 않는다.** 10초 기다린 뒤 무엇을 확인해야 하는지 안내하고 종료한다
- **카메라가 안 열리면 즉시 중단한다.** 예전에 대체 이미지로 넘어가는 경로가 있었는데, 그 때문에 관측 두 건이 저장된 테스트 이미지를 보고 나온 결과였다는 걸 뒤늦게 발견했다. 조용히 가짜 데이터를 쌓는 것이 최악이다
- **에피소드마다 검수 요약을 출력한다.** 프레임 수와 CSV 행 수 일치, 프레임 간격, 오도메트리 수신 건수, 그리고 마지막 3초 이동거리

마지막 항목은 이번에 정한 수집 규칙 때문이다. 목표 앞에 멈춘 뒤 **8초를 그대로 기록해야** 한다. 접근 궤적만 모으면 모델은 "항상 앞으로"만 배우고, 앞 글에서 본 "가까워져도 변위가 안 줄어드는" 증상이 그대로 재현된다. 그 8초가 제대로 들어갔는지를 매 에피소드 숫자로 확인하는 것이다.

데이터 수집 코드에서 가장 위험한 것은 크래시가 아니라 <strong>조용한 성공</strong>이다. 파일이 생기고 프로세스가 정상 종료하면 사람은 확인하지 않는다. 그래서 "이 조건이 아니면 시작하지 않는다"를 코드에 박아두는 편이, 나중에 수십 개를 다시 찍는 것보다 훨씬 싸다.
