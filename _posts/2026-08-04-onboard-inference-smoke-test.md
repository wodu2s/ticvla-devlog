VLM을 로봇에 올릴 때 가장 먼저 걱정한 건 메모리였다. 16GB 통합 메모리에 1B급 VLM과 Action Expert를 동시에 올리고, 거기에 ROS 2 노드와 카메라 파이프라인까지 붙는다. OOM으로 몇 번 깨지겠거니 했다.

전혀 아니었다.

## 스모크 테스트 — 전 스테이지 통과

| 단계 | 시간 | RSS | CUDA 할당 |
|---|---|---|---|
| 환경 정보 | 2.11s | 427MB | — |
| 모델 구조 생성 | 7.37s | 1016MB | — |
| checkpoint 로딩 | 1.68s | 2790MB | — |
| `.to(cuda)` + `.eval()` | 0.92s | 1013MB | 1840MB |
| 추론 ×3 | 43.80s | 1656MB | 1840MB |

CUDA 1.8GB, RSS 1.7GB. 16GB 중 8GB 이상이 계속 비어 있었다. **양자화도, 외부 GPU 서버도 필요 없었다.** 초기 계획에 적어뒀던 "OOM 대비책"은 통째로 폐기했다.

출력도 멀쩡했다.

- waypoints shape `[1, 30, 2]` — 30스텝 action horizon
- NaN / Inf 없음
- 최종 변위 0.519m, 방향 36.9°

그리고 무엇보다, 모델이 장면을 실제로 이해하고 있었다. 벽 옆의 작은 사무실, 앉아 있는 사람, 낮은 테이블을 짚어내고 전진 계획을 세웠다. 논문에서 본 그림이 내 로봇 카메라 앞에서 재현되는 순간이다.

## 그런데 14.11초

```
warmup (1회차)  15.52s
평균            14.11s   (min 14.07 / max 14.15)
```

편차가 0.1초 미만이다. 어쩌다 느린 게 아니라 **구조적으로 14초다.**

왜 치명적인지는 숫자 두 개를 나란히 놓으면 바로 보인다.

```
action horizon = 30 스텝 × 0.1초 =  3초 앞을 계획
추론 소요                        = 14초
```

계산이 끝난 시점에 waypoint는 이미 11초 지난 과거를 기준으로 만들어진 값이다. 3초 앞을 내다본 계획을 14초 뒤에 받는다. **이 상태로는 주행에 쓸 수 없다.**

## 병목은 어디인가

원본 코드의 `predict()`를 보면 두 가지 일을 한 번에 한다.

```python
generated_response = self.vlm.chat(...)              # 텍스트 생성
waypoints = self.action_expert(image_embeds, state,
                               kv_cache=past_key_values)
```

`<think>...</think>` 문장을 토큰 단위로 자기회귀 생성하는 부분이 시간의 대부분일 것으로 보인다. Action Expert는 cross-attention 스택이라 단독 실행은 수십~수백 ms 수준일 가능성이 높다.

만약 그렇다면 길이 하나가 열린다.

```
느린 루프: VLM이 장면을 해석 → KV 캐시 갱신
빠른 루프: 현재 이미지 + 캐시된 의미정보 + 로봇 상태 → Action Expert → waypoint
```

성립 여부는 **`past_key_values`를 여러 프레임에 걸쳐 재사용할 수 있는가**에 달렸다. 재사용이 되면 14초는 "장면을 새로 해석하는 주기"가 되고, 실제 제어 주기는 Action Expert 속도로 내려간다.
