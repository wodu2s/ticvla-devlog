지난 글의 가설을 측정으로 확인했다. `predict()`를 VLM 생성 구간과 Action Expert 구간으로 쪼개 각각 시간을 쟀다.

## 결과

```
VLM 텍스트 생성        23.4초   ← 전부 여기
Action Expert          11.9ms
```

**Action Expert는 VLM의 2000분의 1이다.** 이 숫자 하나로 설계가 정해졌다.

```
느린 루프 (30초)   이미지 → VLM → <think> 생성 → past_key_values 갱신
빠른 루프 (1Hz)    현재 이미지 + 캐시된 KV + 로봇 상태 → Action Expert → waypoint
```

즉 로봇은 **1Hz로 계속 판단하되, 장면 해석만 30초마다 갱신**한다. 14초 지연이 곧 제어 지연이던 구조가 사라졌다.

## `<think>`는 장식이 아니다

여기서 중요한 걸 하나 알게 됐다. 나는 `<think>` 텍스트를 "모델이 왜 그렇게 판단했는지 보여주는 로그" 정도로 생각했다. 아니었다.

```
1. vlm.chat(...)                              → <think>…</think><answer>…</answer>
2. messages = [system, user, assistant(생성물)]  ← 생성물을 대화에 다시 포함
3. apply_chat_template → 토크나이즈 → forward → past_key_values
4. action_expert(image_embeds, state, kv_cache=past_key_values) → waypoints
```

**생성된 텍스트가 다시 forward되어 KV 캐시를 만들고, 그 캐시가 Action Expert의 입력이 된다.** 그리고 브리지는 이 캐시를 다음 주기까지 재사용한다.

한 번 생성된 `<think>` 한 문단이 이후 30초 동안 로봇의 조향을 지배한다는 뜻이다. 환각이 위험한 이유가 여기 있다. 실제로 "왼쪽 유리벽이 위험하다"고 서술하면서 왼쪽으로 가는 사례를 봤다.

그래서 원칙을 정했다.

> 판정은 숫자로, `<think>`는 해석 보조로만.

시연에서 설명할 때도 "모델의 사고 과정입니다"보다 **"모델이 생성한 판단 근거이고, 이 문장이 실제로 조향에 입력됩니다"**가 정확하고 더 인상적이다.

## 30초라는 벽

빠른 루프를 분리해도 사라지지 않는 제약이 하나 남는다. **장면 재해석은 여전히 23.4초마다 한 번**이다.

이것이 의미하는 바를 시나리오에 정직하게 반영해야 했다.

| 가능 | 불가능 |
|---|---|
| 미리 서 있는 사람을 우회 | 갑자기 끼어드는 사람을 회피 |

"실시간 회피"는 이 구조로 안 된다. 데모 시나리오를 **"미리 서 있는 사람을 피해 복도 끝까지"**로 확정했다. 원래 논문의 시나리오 문구와도 일치하니 억지로 축소한 것도 아니다.
